# /dev review — Reviewer 模式

## 执行流程

### 1. 读取上下文

1. **读 AGENTS.md** — 理解项目规则
2. **读 docs/product.md** — 理解需求
3. **读 ARCHITECTURE.md** — 理解架构约束
4. **读 docs/engineering.md** — 理解编码规范

### 2. 确定审查范围

- 检查 `git diff` 和 `git log` 查看最近的改动
- 如果有活跃的 Feature Plan（`docs/plans/active/`），对照计划审查
- 向用户确认审查范围："我看到最近改了这些文件，要审查这些吗？"

### 3. 逐项检查

对每个改动的文件，按以下清单检查：

#### 需求符合性
- [ ] 改动是否满足 `docs/product.md` 中的需求？
- [ ] 是否有多余的改动（超出需求范围）？
- [ ] Acceptance Criteria 是否都被覆盖？

#### 架构一致性
- [ ] 是否遵守 `ARCHITECTURE.md` 中的模块边界？
- [ ] 依赖方向是否正确？
- [ ] 是否引入了不必要的新依赖？

#### 代码质量
- [ ] 是否有重复代码？（可以提取的公共逻辑）
- [ ] 命名是否清晰？（变量、函数、文件）
- [ ] 是否有硬编码的值应该配置化？
- [ ] 错误处理是否合理？

#### 测试覆盖
- [ ] 新功能是否有对应测试？
- [ ] 边界条件是否被测试覆盖？
- [ ] 现有测试是否需要更新？

#### 文档同步
- [ ] 行为变化是否反映在 `docs/product.md`？
- [ ] 架构变化是否反映在 `ARCHITECTURE.md`？
- [ ] 是否有新的 tech debt 需要记录？

### 4. 输出审查结果

使用以下格式输出：

```markdown
## Review 结果

### Critical（必须修复）
- [文件:行号] 描述问题 → 建议修复方式

### Improvements（建议改进）
- [文件:行号] 描述问题 → 建议改进方式

### Acceptable（已确认没问题）
- 列出检查过且没有问题的方面

### 总结
一两句话的总体评价
```

### 5. 跟进

- 如果有 Critical 问题 → 问用户是否现在修复
- 如果需要修复 → 切换到 Builder 模式执行修复
- 修复后建议再次 `/dev review` 确认
